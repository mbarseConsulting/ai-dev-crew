# 0007 — Butler topology, write scope, and the Bash-bypass caveat

## Context

An adversarial audit (`docs/reviews/audit-v2-agents.md`) found three connected contract defects around `agent-crew-butler`:

1. **Topology conflict.** `docs/SPEC.md` §1 said the butler "routes to `agent-crew-dev` and/or `agent-crew-critic`" — implying it dispatches them. `README.md` said "the main session is the orchestrator." Every `crew.sh` kickoff prompt ("Use agent-crew-butler to help with: ...") is worded as an instruction to the session, not a dispatch. If the butler ran as a classic subagent, two of its core behaviors would be in doubt: a subagent has no live conversational channel to the user (`AskUserQuestion` is unavailable to subagents — see ADR 0004), so "ask what's needed" and "hold the architecture dialogue" would at best be a relay, at worst a self-answered monologue; and whether it can dispatch further subagents at all depends on invocation mode.
2. **Write contract.** `docs/SPEC.md` §4 names the butler as the sole writer of `docs/adr/` and `docs/design/`, but `agent-crew-butler.md`'s `tools:` field has no `Write`. The only way to actually create those files without it is a `Bash` heredoc — which quietly defeats the point of the tool-allowlist restriction in the first place.
3. **Overclaimed enforcement.** ADR 0004 stated agents "literally cannot" write or edit outside their allowlist. Both the butler and the critic keep `Bash` in their allowlist, and `Bash` can write files (`echo ... > file`, `sed -i`, heredocs) just as effectively as `Write`/`Edit`. The "mechanically impossible" claim was false for exactly the tool it was trying to rule out.

## Decision

**1. Topology: the butler is a main-session persona, not a dispatched subagent, in normal operation.** A `crew.sh` kickoff (`claude "Use agent-crew-butler to ..."`) starts an interactive session that *adopts the butler's persona and behavior for that session* — it does not dispatch `agent-crew-butler` through the `Agent` tool. Running as the main session gives it what its contract actually needs: a real, iterative conversational channel with the user, and legitimate standing to use its own `Agent` tool to dispatch `agent-crew-dev` and `agent-crew-critic` as subagents. `docs/SPEC.md` §2 now states this explicitly. The butler's agent definition still ships as a normal subagent file (so it *can* be dispatched for a narrower, single-shot routing recommendation if a future workflow needs that), but the canonical flow assumes the main-session case.

**2. Write scope: the butler's `tools:` gains `Write`, behaviorally scoped to `docs/adr/` and `docs/design/` only** — the same pattern already used for the critic's `Write`, scoped to `docs/reviews/`. New allowlist: `Read, Grep, Glob, Bash, Agent, Write`. A new NEVER bullet states the scope explicitly. This makes the butler capable of fulfilling the write contract SPEC §4 already assigned it, without granting it `Edit` (it still cannot silently rewrite existing application code).

**3. Bash-bypass honesty: `tools:` allowlists are guardrails, not sandboxes.** Both the butler and the critic keep `Bash`, and `Bash` can create or modify files regardless of what `Write`/`Edit` restrictions say. This is recorded as an explicit known gap (matching how ADR 0005 already handles its own equivalent limitation) rather than papered over. Both agents get a new NEVER bullet: "Never use Bash to create or modify files (`echo`/`sed`/`tee`/heredoc redirects) — Bash is for running and reading, not writing; use `Write`/`Edit` within their stated scope instead." ADR 0004's Consequences section is amended to state this gap directly instead of claiming the restriction is mechanical when `Bash` remains available.

## Alternatives considered

- **Butler as an advisory subagent** that returns a routing recommendation for the main session to execute, with `Agent` removed from its allowlist. Rejected: this breaks the butler's own contract to hold a live architecture *dialogue* (a subagent gets one shot, not a conversation), and would need yet another indirection layer to get ADRs from "recommendation" into an actual file.
- **Keep the butler write-less and have it draft ADR content as conversational text for the main session or user to save.** Rejected (this was the audit's own fallback option): it breaks "coordination is files" for the flow's single most important artifact, and silently depends on a human or a different agent to complete the write every time.
- **Leave ADR 0004's "mechanically impossible" wording alone** on the grounds that `Edit` specifically is blocked. Rejected: the claim as written ("literally cannot call Edit or Write — the tool isn't in its resolved tool set") is about file mutation in general, and `Bash` mutates files just as surely. An honest claim only about `Edit`/`Write` specifically, with `Bash` called out as a separate, real gap, is the accurate version.

## Consequences

`agent-crew-butler`'s `tools:` becomes `Read, Grep, Glob, Bash, Agent, Write`. It can now actually write the ADRs and design notes `docs/SPEC.md` §4 assigns it, scoped by a behavioral NEVER rather than a path-level tool restriction (path-level enforcement is still deferred to v2.1 hooks per ADR 0006). The topology decision resolves the SPEC-vs-README conflict in favor of "main session = butler" and makes the "ask before dispatching" / "hold the dialogue" behaviors actually exercisable, rather than aspirational. The Bash-bypass acknowledgment means ADR 0004's enforcement claim is now honest but weaker than it originally read: the guarantee is "the specific tools `Edit`/`Write` are absent or scoped," not "this agent cannot possibly write outside its lane" — closing that remaining gap fully requires the path-scoped hooks already deferred to v2.1.
